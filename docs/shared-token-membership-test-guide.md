# 双 Token 套餐上线验收手册

适用分支：`yunb—vip`。按顺序做：先运行自动用例，再验页面和本地 API，最后看升级回调和异常用例。全程使用本地 mock、测试账号和独立数据库。真实支付、真实模型不在这份手册的执行范围。不要在现有业务库改时间、改余额或运行清理命令。

## 0. 上线放行规则

**按第 1 至第 7 节执行，并在每个必测项上留下证据，才进入第 8 节开放。** 本地 mock 通过、页面能打开、支付回调返回 success，都只证明对应环节通过。实际发布还取决于候选版本、数据库、对账和回滚验证。任一项失败或缺证据，状态记为「阻断」，暂停开放给用户。

先记录候选 Git 提交、前端产物版本、后端版本、测试环境、数据库类型、验收人和时间。当前工作区有未提交改动。先固定候选版本，再拿同一份代码和产物做最终验收。桌面登录相关改动单独核对，避免无意混入待发布范围。

| 检查点 | 必须通过 | 放行证据 |
|---|---|---|
| 候选版本 | 前后端版本一致，部署后重新确认 | 提交号、构建记录、部署版本 |
| 数据库 | 保留所有旧数据，会员新增字段和索引齐全，旧套餐仍可购买和扣减 | 增量迁移审阅、备份恢复演练、迁移前后对比 |
| 计费 | 普通 Key 四种偏好、跨渠道分项扣减、钱包隔离、并发和异常收尾正确 | 自动日志、页面和只读 SQL 对账 |
| 升级与支付 | 报价等于实收，原订阅更新，重复回调幂等，冲突可对账 | 签名 mock、受控部署的回调和账单证据 |
| 发布操作 | 能暂停新购买和升级，保留已付款订单与在途结算 | 操作演练、值守与对账负责人 |

当前代码的自动用例使用独立 fixture。**待发布环境的数据库增量迁移、部署后的支付链路和暂停操作仍要验收。** 自动退款未接入，人工对账必须有负责人和操作记录。对历史无档位快照的订阅，运营应确认其可正常继续使用，并接受暂不能升级的范围。

## 4. 本地模型 mock 与分项扣减

仅需要验证核心计费时，第 2 节自动用例已经启动两个 mock。要从页面创建渠道并实测，可以另开终端运行如下 Python mock。只监听本机 `18080`。它返回固定的输入 12、输出 8，并打印每次收到的模型名，方便核对耗尽是否发生转发。

```bash
python3 -u - <<'PY'
import json
from http.server import BaseHTTPRequestHandler, HTTPServer

class MockChat(BaseHTTPRequestHandler):
    def do_POST(self):
        if self.path not in ("/v1/chat/completions", "/mock/one", "/mock/two"):
            self.send_error(404)
            return
        request = json.loads(self.rfile.read(int(self.headers["Content-Length"])))
        print("received:", self.path, request["model"], flush=True)
        response = {
            "id": "mock-chat",
            "object": "chat.completion",
            "model": request["model"],
            "choices": [{"index": 0, "message": {"role": "assistant", "content": "OK"}, "finish_reason": "stop"}],
            "usage": {"prompt_tokens": 12, "completion_tokens": 8, "total_tokens": 20},
        }
        body = json.dumps(response).encode()
        self.send_response(200)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

HTTPServer(("127.0.0.1", 18080), MockChat).serve_forever()
PY
```

后台新增两条独立「自定义渠道」。地址分别为 `http://127.0.0.1:18080/mock/one` 和 `http://127.0.0.1:18080/mock/two`，模型名分别填 `mock-dual-one`、`mock-dual-two`，渠道密钥可用合成值。选与测试账号普通 Key 相同的分组。确认这两个独有模型名在路由中只匹配对应的本地渠道。模型倍率需配置为常规 Token 比例计价，如果未配置，网关会拒绝。若手工部署的出站安全策略拦截 loopback，直接使用第 2 节自动 mock 用例，不要降低业务环境的安全配置。

参考倍率可设为模型倍率 2 和 3、补全倍率 1.5、分组倍率 1，无折扣和附加费。能固定上述倍率时，第一条应扣输入 **24**、输出 **24**，第二条应扣输入 **36**、输出 **36**。如果后台倍率不同，以实际倍率的计算值为准。

普通 Key 调用命令，使用 zsh 执行：

```zsh
read -rs 'API_KEY?粘贴测试普通语言模型 Key（保留 sk-）：'
printf '\n'
for MODEL in mock-dual-one mock-dual-two; do
  curl --max-time 10 -sS -i http://127.0.0.1:3000/v1/chat/completions \
    -H "Authorization: Bearer $API_KEY" \
    -H 'Content-Type: application/json' \
    --data "{\"model\":\"$MODEL\",\"messages\":[{\"role\":\"user\",\"content\":\"Reply OK\"}],\"max_tokens\":32,\"stream\":false}"
done
unset API_KEY
```

- [ ] **B01 分项扣减**：两条均返回 200。用同一个普通 Key，两条请求扣同一期 A 的输入、输出，不新建渠道余额。请求完成后预留归零，钱包调用前后不变。
- [ ] **B02 单项不足**：用小额度的独立测试套餐，使输入或输出任一项不满足预留。选「仅订阅」调用，预期 403，mock 终端没有新 `received`。另一个维度余额也不减少。输入预留和输出预留是上界，可能比 mock 的最终用量大。
- [ ] **B03 订阅优先允许兜底**：启用套餐的「允许钱包余额兜底」后购买新的测试订阅。额度不足时整笔转钱包，订阅两项不扣。已购买的订阅保留购买时的兜底设置，编辑套餐不改变该期的设置。
- [ ] **B04 禁止兜底**：单独买一份关闭兜底的测试套餐。订阅优先且额度不足时 403，钱包不变。
- [ ] **B05 钱包优先 / 仅钱包**：钱包够用时先扣钱包，两项额度不变。钱包不足时「钱包优先」尝试订阅，「仅钱包」直接拒绝。钱包不足场景可以用自动测试完成，无需改数据库余额。
- [ ] **B06 边界**：当前双 Token 只支持可分项、带明确输出上限的常规 Chat 文本。无上限、按次、不可拆阶梯、媒体接口不应扣双 Token。是否转钱包由计费偏好和兜底设置决定，建议用「仅订阅」验证拒绝。普通旧 quota 套餐与现有钱包计费由第 2 节回归。

## 5. 升级报价、周期与回调

### 页面，只预览

1. 用已买 A 的合成用户打开「钱包 → 我的订阅 → 升级套餐」，或者直接打开「会员中心」的「我的会员」。
2. 选 B。确认对话框显示 B、应付金额、输入与输出各补多少、升级后各自可用多少和原到期日。报价会短时失效，过期请重新选择目标档。
3. 只验页面时可以关闭弹窗，不需要真实支付。关闭后档位、到期时间和额度保持原值。
4. 试选不同周期或非更高档位，预期服务端拒绝。原套餐下架时，已保存的订阅快照仍是报价基准。

### 精确算例，通过自动用例固定时间

| 场景 | 预期 |
|---|---|
| A 30 天，剩余 5 天，B 售价 90 | 应付 **15.00**，不是 A、B 差价。 |
| B 输入 250 万、输出 50 万，当前额度周期也剩 5/30 | 新增 **416,666 输入 / 83,333 输出**。A 剩余输入 10 万、输出 0 时，升级后可用 **516,666 输入 / 83,333 输出**。 |
| 年付、月重置 | 金额用原年有效期的剩余比例。补发量用当前月额度周期剩余比例。两条时间轴独立。 |
| A 升 B 后再升 C | 以 B 判断 C 是否为更高档位，C 全价和完整额度按原订阅及当前周期的剩余比例折算。保留已有余额和历史使用，仍更新同一订阅。 |
| 到达下一重置周期 | 新周期按已生效档完整发放。上周期的余额不滚入，上个周期的在途请求终态不扣新周期。 |

### 支付与异常，通过本地签名通知模拟

- [ ] **U01 付款前**：只有报价或待付款订单时不补额度。
- [ ] **U02 付款成功**：同一订阅 ID 的档位更新。两个额度上限各增加报价补发量，已用及在途预留保留。开始、到期与当前重置时间不变。原普通 Key 仍然可用。
- [ ] **U03 重复通知**：同一笔订单重复通知，额度只增加一次。
- [ ] **U04 并发付款**：不同升级订单基于同一旧档同时成功回调，仅一笔更新档位。另一笔账单为「已收款，待对账」。
- [ ] **U05 付款后失效**：已支付且回调时原订阅已到期、周期已切换或当前档已变化，不应补额度。对账记录保留订单号及金额，实际退款由管理员处理。
- [ ] **U06 错误签名、金额不符和报价篡改**：不生效、不调整额度。现有 Epay mock 用例同时覆盖普通购买的签名和金额校验。
- [ ] **U07 周期与连续升级**：用第 2 节测试验证，不需要在运行中的数据库改时间或等待下一月。
- [ ] **U08 旧订阅隔离**：钱包账户、旧 quota 套餐、普通购买和旧周期重置正常，升级不会把旧 quota 转成输入或输出 Token。

## 7. 发布前阻断检查

### 7.1 数据库和候选版本

- [ ] 由维护人审核**只增加必要结构的上线迁移**，在与实际部署同类型的数据库副本上演练。增量脚本和执行结果是上线材料的一部分。本手册的 SQL 都是只读查询，不能充当迁移脚本。项目的完整 master 启动迁移有历史删表、删列逻辑，不用它替代本次审查。
- [ ] 对业务库做可恢复备份，并在独立环境实际验证能恢复。核对历史订阅、订单、余额、两维额度和日志；行数、关键记录与索引应符合预期。任何现存权益被重置、覆盖或删除都阻断。
- [ ] 用候选版本在目标数据库方言跑第 2 节关键用例。独立 SQL fixture 的 DSN 只能来自专用只用于测试的 loopback 容器，不能传业务 `.env`、真实账号凭证或可写业务副本。
- [ ] 针对升级和周期新增项，确认**在当前实际部署的日／月边界**重置一次。多实例环境确认时钟、时区和报价签名密钥配置一致，回调打到不同实例也只结算一次。
- [ ] 钱包和旧 quota 套餐做一次端到端对照，覆盖普通购买、已购套餐额度扣减、定时重置，以及会员额度不足时的兜底开关。测钱包扣减时用合成测试余额。

### 7.2 钱和 Token 对账

- [ ] 在隔离的候选部署做一次**完整的 mock 付款**。从用户点击报价、确认订单金额、付款通知、返回页，一直到原订阅更新。核对订单号、报价金额、实收金额、档位、分项上限和到账时间。只测回调函数不足以证明部署上的网关配置无误。
- [ ] 做一次使用错误签名或错误金额的 mock 回调，订单与权益不被改。做两次合法重复通知，只有第一笔产生权益变化。
- [ ] 单独检查两笔并发订单、跨周期到达、到期后到达。确认异常订单可在账单历史中查到「已收款，待对账」，订单能按订单号查到金额及原因。确认异常订单不会按正常开通处理，也不会自动补发给另一期订阅。
- [ ] 对账负责人用一笔合成异常单演练：按订单号关联支付流水和订阅记录，确认待退款金额，记录处理人、处理时间、外部退款流水及最终结果。演练不发真实退款。未建立此操作记录和异常处理入口时，**阻断升级支付开放**。
- [ ] 实际支付提供方的路由、签名、回调可达性和返回页须在你授权的测试环境手工验收。若暂时维持全 mock，公开售卖和真实升级支付仍是待放行项。不要用真实用户的第一笔付款代替验收。
- [ ] 逐个拟开放的模型实例核对确实遵守输出上限，能返回完整输入／输出用量，并按对应倍率出账。只用已获授权的测试方式核对。没有可信证据的实例不列入首批用户可用范围，特别是按次、媒体和未支持的计费模式。
- [ ] 检查无用量、客户端取消、断流和请求结果不明。此类请求进入待核对，不能二次扣钱包或自动清预留。准备好按请求 ID 和订阅 ID 排查的方法，再上线值守。

### 7.3 上线操作与回滚演练

- [ ] 上线前在测试环境演练**暂停新购买和升级入口**。用现有套餐停用和部署入口管理措施，核实用户端和直接 API 均不能为已暂停目标新下单。已有待付或已付款订单继续可回调和对账。
- [ ] 在有已购订阅或支付在途时，不直接回退到不了解新订单或新周期的老后端。优先暂停新交易，保留支持新账本的结算服务，处理完待付款、待对账和在途请求后，再执行演练过的版本回退。
- [ ] 保留新增表、字段、订单和账本。回滚演练验证旧客户端与旧订阅访问，数据库中不执行 DROP，不覆盖上线后新增的支付记录。

## 8. 限量开放和扩大范围

1. **测试账号**先验证上线产物，重复第 3 节的页面关键路径和第 5 节的报价。这里只使用已审批的测试账户、渠道和支付环境。
2. **少量授权用户**使用经第 7 节验证过的套餐、渠道和支付方式。配置小规模配额，确定值守负责人和观察窗口。
3. 在扩大范围前逐笔对照首批订单和请求。检查支付实收是否等于报价、升级是否更新原订阅、两项扣减是否符合现有倍率、钱包兜底是否符合用户偏好，以及预留和待对账是否持续增加。
4. 发现重复发放、错误扣钱包、越过余额上限、账单对不上或无法定位已付款异常单，立即暂停新增购买和升级，保留已有调用与回调的结算证据。修复并重复对应阻断项后再开放。
