# 套餐预计毛利润（扣费加价比例）

## 配置及公式

在 `/subscriptions` 新增或编辑套餐时填写“预计毛利润（%）”，范围 0～100，最多两位小数，默认 0。

当前口径：`发放点数 = 套餐价格 × 点数比例`；`实际扣点 = 加价前计费金额 × (1 + 百分比 / 100) × 点数比例`。内部使用 quota 整数保存点数最小单位，最后统一取整；历史比例 0 按 1 扣点并保留手工发放额度。
例如价格 30、点数比例 2，发放 60 点；加价前计费金额 1 元、加价 30%，扣除 2.6 点。点数比例与毛利润加价是两个独立配置。
此字段不是财务毛利率，也不承诺上游成本硬上限。加价前金额是站内费率算出的金额，不是经过上游账单核验的真实采购成本；点数比例不能用于承诺人民币上游成本硬上限。

## 数据及兼容

- `subscription_plans.gross_profit_percent`：后台配置，decimal(5,2)，默认 0。
- `user_subscriptions.gross_profit_percent`：购买/管理员绑定时的快照，decimal(5,2)，默认 0。
- 两表已在现有 AutoMigrate 列表中。部署更新后的后端并由主节点成功迁移后，再使用新版表单；不需要新建表。
- 修改套餐仅影响之后开通的订阅。现有已购订阅继续按原快照，历史订阅默认不加价。
- 任务快照使用现有 `tasks.private_data` JSON 的 `subscription_gross_profit_percent`，退款按已扣原额退还。
- 回滚业务配置时将套餐比例设为 0；已经开通的订阅保留购买快照。回滚程序可以保留新增列，不要直接删除已用快照。

## 扣费链路

模型原计价（含原有用户折扣）→按选中订阅快照加价→统计/日志/最终结算。
预扣及追加预留使用同一份点数比例和毛利润快照；失败退款使用已经预扣的点数，不二次乘倍率。
文本、音频、实时请求及异步任务结算均传递该比例。钱包和企业资金来源不加价。
后台日志记录订阅 ID、比例和实际扣费额度；消费日志 `other.admin_info.subscription_gross_profit_percent` 标记本次比例。
本次没有修改现有模型费率、分组倍率、支付金额、套餐余额或钱包兜底策略。

## 点数比例与管理员审计

- 新增 `subscription_plans.points_ratio`，套餐新增/编辑后由服务端重新计算 `total_amount`，忽略客户端传入的不一致额度。0 表示兼容旧手工额度；正比例不能与零价格生成不限额套餐。
- `user_subscriptions.points_ratio` 保存购买快照；修改套餐不追溯修改已购订阅。异步任务同时保存比例到 private_data。
- 管理员日志列表及详情展示加价前扣费金额和点数比例，快照放在 `other.admin_info` 中；普通用户接口剥离这些字段。旧日志没有快照时显示空值，不倒推伪造。
- 订阅点数交易不改变用户、API Key、渠道的金额累计；按订阅额度预扣/结算，不扣 API Key 的金额余额。
- 小时报表通过 `quota_data.subscription_quota` 独立保存点数，`quota_data.quota` 只保存金额；实际请求数和 Token 数仍然统计。
- 套餐卡与购买确认按当前币种显示售价，额度显示点数。当前人民币配置显示 ¥30，不额外乘汇率。
- 部署需先由主节点完成套餐、用户订阅、日志及 quota_data 的自动补列，再切流量。旧在途异步任务建议先完成，历史金额统计本次不回填。

本轮新增隔离验证：1 元 × 1.3 × 2 = 2.6 点；有限额度 API Key 的金额余额/已用额不变；渠道金额累计不变；报表金额仅包含钱包交易而点数单列；管理员审计包含原金额与比例，普通用户日志移除 admin_info；创建/更新管理接口按价格和比例计算发放额度。
