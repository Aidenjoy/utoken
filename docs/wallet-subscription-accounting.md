# 钱包总用量与订阅调用隔离

## 1. 实际修改内容

- `users.used_quota` 的新增长仅来自钱包调用消费和每笔成功购买套餐的金额。
- 新增 `users.subscription_request_count bigint not null default 0`，记录实际使用订阅资金来源的调用次数。
- `users.request_count` 继续包含钱包和套餐调用，购买订单、任务补扣和退款不作为新调用。
- 钱包页面显示“当前余额 / 总用量 / API 请求数 / 套餐请求数”；总用量说明调整为钱包消费与套餐购买支出。

## 2. 修改原因

原先套餐调用会增加钱包总用量，任务退款还会减少它；异步补扣会额外增加请求数。现在将金额累计和真实请求计数分开。

## 3. 涉及文件

- `model/user.go`：账户字段、来源感知统计入口、保护计数不被通用用户更新覆盖。
- `model/utils.go`：批量/Redis 增量及最终用户行更新支持套餐计数。
- `model/subscription.go`：第三方支付订单完成及钱包购买在各自事务内累计购买金额。
- `service/text_quota.go`、`service/quota.go`、`service/task_billing.go`、`service/violation_fee.go`、`relay/mjproxy_handler.go`：按照实际资金来源统计，订阅调用不累计钱包金额。
- `controller/user.go`：self 接口返回套餐调用次数。
- `web/default/src/features/wallet/` 及各语言包：展示独立套餐请求数。

## 4. 关键代码及公式

| 行为 | 钱包余额 quota | 总用量 used_quota | 总请求 request_count | 套餐请求 subscription_request_count |
|---|---|---|---|---|
| 第三方购买成功 | 不变 | 加购买金额对应 quota，一次 | 不变 | 不变 |
| 钱包购买成功 | 减购买金额对应 quota | 加同一额度，一次 | 不变 | 不变 |
| 套餐调用 | 不变 | 不变 | +1 | +1 |
| 钱包调用 | 按实际消费扣减 | 加实际消费 | +1 | 不变 |
| 套餐调用补扣/退款 | 不变 | 不变 | 不变 | 不变 |

购买金额沿用现有余额购买的金额到内部额度换算：`ceil(订单 money × QuotaPerUnit)`，不使用套餐 total_amount 或毛利润倍率。当前项目展示汇率为 1、QuotaPerUnit 为 500000 时，售价 30 对应 15000000 quota，展示为 30。

套餐扣费和毛利润比例继续作用于 `user_subscriptions.amount_used`；调用日志及渠道用量继续保留实际消耗。真实调用计数沿用现有调用完成统计入口，不通过补扣、退款或支付回调增加。

第三方支付在锁定订单后检查状态；成功订单直接返回。购买金额累计、订阅开通、支付流水和订单完成在同一事务中，任一步失败均回滚。

## 5. 风险与兼容

- 保留原有工作区改动，没有更改模型倍率、套餐价格、已有余额或计费偏好。
- 新计数字段从 0 开始；不回填历史请求，不修正历史混合 used_quota。
- 通过现有 User AutoMigrate 自动补列。部署时先完成主节点迁移，再切换新版本流量。
- 可回滚程序并保留新增字段；不要删除计数历史或清空账户金额。
- 金额换算沿用既有套餐购买口径；此修改不重新定义各支付渠道币种及汇率规则。

## 6. 验证步骤

使用独立内存 SQLite，通过模拟 HTTP 支付完成入口、实际 PostTextConsumeQuota、实际异步退款/补扣、self 接口及批量刷新核对字段变化。未访问真实支付或千帆。

## 7. 验证结果

已通过：

- Go model/service/controller/relay 编译检查。
- 前端 typecheck 和生产构建。
- 已有支付渠道校验、任务退款/差额结算、批量余额预检回归测试。
- 重复回调只计一次金额；第三方购买不改变钱包余额。
- 套餐调用保留 30% 加价，钱包金额不变，总请求和套餐请求各 +1。
- 钱包调用正常扣余额并累计总用量，只增加总请求数。
- 套餐任务退款和补扣不改变钱包总用量，不重复增加请求数。
- 钱包购买同时扣余额、增加总用量，不增加请求数。
- self HTTP 响应包含 subscription_request_count。
- 购买流水写入失败时，金额累计和订阅开通一起回滚。
- 批量模式只累计钱包金额，并正确增加两类请求计数。

当前业务数据库迁移、线上支付及上游调用未执行；未通过 Apifox 验证，使用隔离模拟 HTTP 完成接口核对。

## 8. 改动总结

金额按资金来源隔离，请求按真实调用入口计数；购买支出与套餐内的额度使用分别记账。

## 9. 改前与改后

改前：购买不计总用量，套餐使用计总用量，异步补扣也加请求数。

改后：购买金额计一次，套餐使用只改套餐额度与调用计数，补扣和退款不计新请求。

## 后续点数计费补充

订阅消费按 `加价前计费金额 × (1 + 毛利润百分比 / 100) × 购买时点数比例` 扣点。
除用户钱包金额外，API Key 金额余额/用量、渠道金额累计以及 quota_data 金额也与点数隔离；报表新增 subscription_quota 单列保存点数。
每笔成功购买的实付金额仍按原规则计入钱包总用量一次。普通请求数及订阅请求数继续累计。
管理员可看加价前金额与比例快照，普通日志不暴露 admin_info。
